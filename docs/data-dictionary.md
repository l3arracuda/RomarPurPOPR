## รหัสที่ต้องรู้

### `POC_RCVH.DOCTYP` — ประเภทเอกสารรับ
| ค่า | Prefix | ความหมาย | แถว | ยอดรวม |
|---|---|---|---|---|
| `R` | PR1 | รับเข้าซื้อ (ปกติ) | 123,870 | +9,969 ล้าน |
| `T` | PT1 | **ส่งคืนผู้ขาย** — QTY/AMT เป็นค่าติดลบ | 4,171 | −31.2 ล้าน |
| `B` | PB1 | ใช้แค่ 2 ใบ ปี 2015–16 (ตกยุค) | 2 | 5,299 |

→ **ยอดรับสุทธิ = SUM(QTY) ของ DOCTYP IN ('R','T')** หักส่งคืนอัตโนมัติ

### `POC_POH.APPSTS` — ธงสถานะงานของใบสั่งซื้อ ★ สำคัญที่สุดในระบบ

| ค่า | ความหมาย | แถว | ช่วงปี |
|---|---|---|---|
| `P` | **ปิดงานแล้ว** | 60,015 | 2011–2026 |
| `A` | เปิดอยู่ ยังไม่เคยรับของเลย | 118 | 2003–2026 |
| `T` | เปิดอยู่ รับบางส่วนแล้ว | 187 | 2005–2026 |
| `C` | เลิกใช้แล้ว | 2,266 | 2011–2016 เท่านั้น |

**`APPSTS = 'P'` คือการปิดงาน** ซึ่งจัดซื้อกดเองเมื่อตัดสินใจว่าจบงานแล้ว
แม้ของจะยังรับไม่ครบก็ตาม นี่คือคำตอบของคำถาม "ปิด PO ด้วยมือเก็บไว้ที่ไหน"

### สูตรสถานะ ปิด / ค้างรับ

```
ค้างรับ  <=>  APPSTS <> 'P'  และ  (จำนวนสั่ง - จำนวนรับ) > 0
ปิด      <=>  กรณีอื่นทั้งหมด
```

พิสูจน์กับรายงาน `pcsr0511` จำนวน **687 บรรทัด ลงตัวทุกบรรทัด ไม่มีข้อยกเว้น**

| APPSTS | ยอดค้าง | สถานะในรายงาน | จำนวน |
|---|---|---|---|
| `A` | > 0 | ค้างรับ | 10 |
| `T` | > 0 | ค้างรับ | 4 |
| `T` | ≤ 0 | ปิด | 12 |
| `P` | ≤ 0 | ปิด | 647 |
| `P` | **> 0** | **ปิด** | **14** ← ปิดด้วยมือทั้งที่ยังค้าง |

> 📌 **บันทึกความเข้าใจผิดที่เคยเกิดขึ้น** (อย่าวนกลับไปอีก)
> 1. เคยเดาว่า `T` = ยกเลิก → ผิด `T` คือใบที่ยังเปิดอยู่และกำลังรับของ
> 2. เคยเดาว่า `A` = รออนุมัติ แล้วตัดออกจากยอดค้าง → ผิด ERP นับเป็นค้างรับ
> 3. เคยสรุปว่ารายงานไม่สนใจ `APPSTS` เลย → ผิด `APPSTS` คือตัวหลักต่างหาก
>
> สาเหตุที่หลงทางคือทดสอบกับตัวอย่างน้อยเกินไป (11 บรรทัด) ซึ่งกฎสองแบบ
> ให้คำตอบเหมือนกันพอดี ต้องใช้ชุดใหญ่ (687 บรรทัด) ถึงจะแยกออก

### `qtyrcv` ของ ERP ไม่หักยอดส่งคืน

`qtyrcv` ในรายงาน = `POC_POD.RCVQTY` ซึ่งนับเฉพาะใบรับ `PR1` **ไม่หักใบส่งคืน `PT1`**
เช่น `PP1-69-02617` บรรทัด 1 รับ 2,000 คืน 3 → ERP แสดง 2,000 ไม่ใช่ 1,997

คลังข้อมูลของเราจึงแยกเป็น 3 คอลัมน์ คอลัมน์หลักตรงกับ ERP เพื่อให้กระทบยอดกันได้
ส่วนยอดสุทธิมีไว้ให้เห็นความจริง:

| คอลัมน์ | ความหมาย |
|---|---|
| `RcvQty` | รับเข้า ไม่หักส่งคืน — **ตรงกับ `qtyrcv` ของ ERP** |
| `RetQty` | ส่งคืน (ค่าติดลบ) |
| `RcvQtyNet` | รับสุทธิ = `RcvQty + RetQty` |
| `OpenQty` | ค้างตามนิยาม ERP — **ตรงกับ `qtybal`** |
| `OpenQtyNet` | ค้างหลังหักส่งคืน |

`POC_RCVH.APPSTS` = `'A'` ทุกแถว → ไม่ต้องกรอง
`POC_POH.POTYP` = `'1'` ทุกแถว → ไม่ต้องแยกประเภท

## คอลัมน์สำคัญ

### `POC_POD` (รายการ PO)
`DOCNO, SEQ, PDTCD, QTY, UNIT, PRICE, PACKSIZE, AMT, RCVQTY, RCVAMT, sShipDat, ShipDat, ADDUSERID`
- `AMT` = QTY × PRICE (ก่อน VAT)
- `NETAMT1 / VATAMT / NETAMT2` = **0 เสมอ** ห้ามใช้ — VAT คิดที่ header เท่านั้น
- `PACKSIZE` ≠ 1 ใน **7,494 บรรทัด** → หน่วยซื้อ ≠ หน่วยสต็อก ต้องระวัง

### `POC_RCVD` (รายการใบรับ)
`DOCNO, SEQ, POSEQ, PDTCD, QTY, UNIT, PRICE, PACKSIZE, AMT, RetQty, LOCCD(ว่าง)`
- `PRICE` = ราคาจาก PO เสมอ (ตรวจแล้ว) → `AMT = QTY × PRICE`
- `POSEQ` มีค่าครบ 100% → match แม่นยำระดับบรรทัด
- `RetQty` ≠ 0 ใน 4,129 แถว

### `POC_POH` / `POC_RCVH` (หัวเอกสาร)
`DOCNO, DOCDAT, SUPCD, PONO(ใน RCVH), SHIPDAT, DUEDAT, TLTAMT, DISPCT, DISAMT, VATPCT, VATAMT, NETAMT, REM, APPSTS, ADDUSERID, ADDDATTIM`
- `EXTNO` ใน RCVH = เลขเอกสารผู้ขาย (ในภาพคือ 1971)
- `DUEDAT = 1899-12-30` คือค่าว่าง (TDateTime 0) → ต้อง `NULLIF`

## กับดักที่เจอมาแล้ว (อย่าพลาดซ้ำ)

### 1. `SEQ` และ `POSEQ` ถูก pad ช่องว่าง **ข้างหน้า**
ค่าจริงคือ `'  1'` ไม่ใช่ `'1'` → `RTRIM()` อย่างเดียวไม่พอ ต้อง `LTRIM(RTRIM())`
ถ้าใช้คีย์นี้ข้ามระบบ (เช่น ส่งไป Python) ต้อง trim ทั้งสองด้าน

### 2. ห้ามครอบฟังก์ชันบนคอลัมน์ที่ใช้ join เด็ดขาด
```sql
-- ผิด : เครื่อง 2008 เลิกใช้ index แล้ว scan เต็มตาราง query ค้างเกิน 10 นาที
LEFT JOIN rcv r ON r.PoNo = LTRIM(RTRIM(pd.DOCNO))
-- ถูก : 6 วินาที
LEFT JOIN rcv r ON r.PoNo = pd.DOCNO
```
T-SQL เทียบ `=` โดยไม่สนช่องว่าง**ท้าย**อยู่แล้ว และช่องว่าง**หน้า**มีเท่ากันทั้งสองฝั่ง
จึงเทียบตรง ๆ ได้ ให้ย้ายการ trim ไปอยู่ใน SELECT list เท่านั้น

### 3. ไม่มีฟิลด์ "ปิด PO" ในฐานข้อมูล — สถานะปิดถูก **คำนวณ** เอา

ตรวจแล้วว่าไม่มีการลบเอกสารเกิดขึ้นจริง:

| การตรวจ | ผล |
|---|---|
| เลขที่ `PP1-69-*` | 2,801 ใบ ครอบคลุม 1–2801 **ไม่มีรูเลยแม้แต่เลขเดียว** |
| เลขที่ `PP1-68-*` | 4,153 ใบ ครอบคลุม 1–4153 **ไม่มีรู** |
| เลขลำดับบรรทัดใน PO (2024+) | ต่อเนื่องทุกใบ **ไม่มีรู** |
| ใบรับกำพร้า (2024+) | **0** (ที่เจอ 599 ใบเป็นของปี 2011–2012 อ้าง PO ก่อนระบบเริ่ม) |

รายงาน `ปิด` / `ค้างรับ` ที่จัดซื้อใช้อยู่จึงเป็นค่าที่**คำนวณจากจำนวนรับเทียบจำนวนสั่ง**
ไม่ได้เก็บไว้ในฐานข้อมูล และรายงานนั้นฝังอยู่ในตัวโปรแกรม (ตรวจ `ReportServer` แล้วว่าง)
อ่านสูตรต้นฉบับจาก SQL ไม่ได้

## ความสัมพันธ์ PO กับ PR (ตรวจจากข้อมูลทั้งหมดแล้ว)

### 1 PO มีได้หลาย PR — **ใช่**

| ใบรับต่อ 1 PO | จำนวน PO (2024+) |
|---|---|
| 1 ใบ | 8,844 |
| 2 ใบ | 1,775 |
| 3 ใบ | 600 |
| 4–8 ใบ | 573 |
| 9–20 ใบ | 32 |

### 1 PR อ้างได้หลาย PO — **ไม่ได้**

`POC_RCVH.PONO` เป็นคอลัมน์เดี่ยวที่ระดับหัวเอกสาร ส่วน `POC_RCVD` ไม่มีคอลัมน์
เลขที่ PO ของตัวเอง มีแค่ `POSEQ` ที่ชี้บรรทัด ดังนั้นใบรับ 1 ใบผูกกับ PO ได้ใบเดียวเสมอ

ตรวจกับข้อมูลทั้งหมด (128,036 ใบ ตั้งแต่ปี 2011):

| การตรวจ | ผล |
|---|---|
| หัวใบรับที่ใช้เลขเดียวกันซ้ำ | **0** |
| ใบรับที่อ้าง PO มากกว่า 1 ใบ | **0** |
| ใบรับที่ `PONO` ว่าง | **0** |

→ คีย์จับคู่ที่ใช้อยู่ (`RCVH.PONO` + `RCVD.POSEQ` → `POD.DOCNO` + `POD.SEQ`)
ครอบคลุมครบถ้วน ไม่มีเคสหลุด

### แต่ของจริง: ใบส่งของผู้ขาย 1 ใบ ครอบได้หลาย PO

ระบบรับมือโดย**แตกเป็นใบรับหลายใบ ใบละ PO** แล้วให้ทุกใบใช้เลขเอกสารผู้ขาย (`EXTNO`) เดียวกัน

ปี 2024+ มี **2,788 ครั้ง** ที่เลขเอกสารผู้ขายใบเดียว (ผู้ขายเดียวกัน วันเดียวกัน)
ครอบ PO มากกว่า 1 ใบ รวม 9,202 คู่ ตัวอย่างจริง:

```
S-01-001  ELD260803  10/09/2026  →  11 PO  /  12 ใบรับ
S-20-0005 690357     05/09/2026  →  10 PO  /  14 ใบรับ
```

→ ถ้าจัดซื้ออยากเห็น "ของที่มากับใบส่งของใบนี้" ต้องจัดกลุ่มด้วย `EXTNO`
ไม่ใช่เลขที่ใบรับ

> ⚠️ `EXTNO` มีค่าขยะเยอะ — `00000` และ `0000` ถูกใช้ซ้ำข้ามปี
> (ตัวอย่าง: `S-07-0002` + `00000` โผล่ใน 98 PO กินเวลา 946 วัน)
> ถ้าจะจัดกลุ่มด้วย `EXTNO` ต้องกรองค่าที่เป็นศูนย์ล้วนออกก่อน

### เคสเก่า: `PONO` ไม่ตรงกับ `RefPoNo`

มี 2,300 ใบ แต่ **เกิดเฉพาะปี 2011–2016 ไม่มีเลยตั้งแต่ 2017**
เป็นการต่อเอกสารเป็นลูกโซ่ คือ `PONO` ชี้ใบ `PT1` ที่เป็นแม่ ส่วน `RefPoNo`
ชี้ใบสั่งซื้อ `PP1` ต้นทาง ไม่กระทบหน้าต่างข้อมูล 2024+ ที่เราใช้
