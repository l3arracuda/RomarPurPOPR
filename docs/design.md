# ออกแบบระบบ — ติดตามการสั่งซื้อและรับเข้า (PO vs GR)

## 1. โจทย์

จัดซื้อเปิด PO → ของเข้าที่สต็อก → เอกสารรับเข้าวิ่งตรงไปบัญชี → **จัดซื้อตกขบวน**
ไม่มีหน้าจอไหนใน ROM ที่ตอบได้ว่า "สั่งไปเท่าไหร่ ได้ของมาแล้วเท่าไหร่"

### ผู้ใช้

| กลุ่ม | ใช้ทำอะไร | ความถี่ |
|---|---|---|
| เจ้าหน้าที่จัดซื้อ (BUNYARAT, KANYARAT, WARAPONG, SUKANYA) | วันนี้ของเข้าอะไรบ้าง / ของตัวเองค้างอะไร | ทุกวัน |
| หัวหน้าจัดซื้อ | ภาพรวมรายเดือน ประเมินผู้ขาย | รายสัปดาห์–เดือน |
| บัญชี | กระทบยอดของค้างรับ (accrual) | สิ้นเดือน |

### คำถามที่ระบบต้องตอบ

1. วันนี้/สัปดาห์นี้ ของเข้ามาอะไรบ้าง จาก PO ใบไหน มูลค่าเท่าไหร่
2. เดือนนี้สั่งไปกี่บาท รับเข้ามาแล้วกี่บาท
3. ตอนนี้ค้างรับทั้งหมดกี่บาท เกินกำหนดกี่บาท
4. PO ใบไหนรับครบ / รับบางส่วน / ยังไม่รับ / รับเกิน
5. ผู้ขายเจ้าไหนส่งตรงเวลา เจ้าไหนส่งช้า

## 2. ผลสำรวจข้อมูลจริง (เฟส 0 — เสร็จแล้ว)

รายละเอียดเต็มอยู่ใน [data-dictionary.md](data-dictionary.md) สรุปเฉพาะที่กระทบการออกแบบ:

| ข้อค้นพบ | ผลต่อการออกแบบ |
|---|---|
| คีย์จับคู่คือ `RCVH.PONO` + `RCVD.POSEQ` → `POD.DOCNO` + `POD.SEQ` และ **orphan = 0 แถว** | จับคู่แม่นยำระดับบรรทัด ไม่ต้องเดา |
| ใบรับทุกใบอ้าง PO เสมอ (`PONO` ไม่เคยว่าง) | ไม่ต้องทำรายงาน "รับลอย" |
| ส่งคืนเป็นเอกสาร `DOCTYP = T` (PT1) ที่ QTY **ติดลบอยู่แล้ว** | `SUM(QTY)` ของ R+T = ยอดรับสุทธิ หักคืนให้อัตโนมัติ |
| `POC_POD.RCVQTY` **เพี้ยน 599 / 23,778 บรรทัด (2.5%)** | ห้ามใช้เป็นแหล่งความจริง ต้อง SUM จาก `POC_RCVD` แล้วทำ exception report จับส่วนต่าง |
| **รับเกิน PO 2,097 บรรทัด (8.8%)** หมายเหตุผู้ใช้ระบุ "ตกเศษไม่พอผลิตซื้อต่อเยอะ" | "รับเกิน" คือสถานะปกติของธุรกิจ ไม่ใช่ error |
| `POC_RCVD.LOCCD` ว่างเปล่า ที่เก็บอยู่ใน `INV_TRN` (`DOCTYP = I1`) | ถ้าต้องการคอลัมน์ "ที่เก็บ" ต้อง join `INV_TRN` เพิ่ม |
| `POH.APPSTS = A` คือรออนุมัติ (206/206 บรรทัดยังไม่เคยรับเลย) | ต้องแยกออกจาก "ค้างรับ" ไม่งั้นตัวเลขค้างพองเกินจริง |
| `PACKSIZE` ไม่เท่ากับ 1 ใน 7,494 บรรทัด | หน่วยซื้อไม่เท่าหน่วยสต็อก เทียบจำนวนต้องระวัง |
| **ปี 2021–2023 ไม่มีข้อมูลเลย** ทั้ง POH, RCVH, INV_TRN | รายงานย้อนหลังทำได้แค่ **2024 เป็นต้นมา** ต้องแจ้งผู้ใช้ชัดเจน |
| มี `INV_TRN` 3 แถวลงวันที่ปี 2038 | ต้องกรองวันที่ผิดปกติออกจากทุกรายงาน |

### ตัวเลขฐาน (PO ปี 2024 ถึงปัจจุบัน 23,778 บรรทัด)

```
มูลค่าสั่งรวม   260,415,122 บาท
รับมาแล้ว       254,803,921 บาท
ค้างรับ          15,535,407 บาท

รับครบ 20,014 | รับเกิน 2,097 | รับบางส่วน 590 | ยังไม่รับ 794 | รออนุมัติ 205 | ยกเลิก 78
```

## 3. สถาปัตยกรรม

```
ROM ERP (SQL Server 2008)  192.168.2.2 / Romar1   << READ-ONLY, บอบบาง >>
        |
        |  SELECT เท่านั้น, ดึงเป็นช่วง ๆ ไม่ยิงสด
        v
ETL (Python)            full ทุกคืน + incremental ทุก 15 นาที
sql/extract/*.sql       กรองส่วนที่เปลี่ยนด้วย ADDDATTIM / UPDDATTIM
        |
        v
คลังข้อมูล               dev : SQLite (ไฟล์เดียว)
ตาราง + index ของเราเอง   prod: SQL Server 2022   <- สลับด้วย .env
        |
        v
เว็บแอป (FastAPI)        Dashboard + ตาราง filter/sort
+ ปุ่ม Export Excel       xlsxwriter
```

### ทำไมต้องมีคลังข้อมูลคั่นกลาง ไม่ยิงสดใส่ ERP

1. **ปกป้องเครื่องที่บอบบาง** ผู้ใช้หลายคนกดรีเฟรชพร้อมกันจะไม่ไปลงที่เครื่อง 2008 เลย
2. **สร้าง index ได้** บน ERP เราแตะอะไรไม่ได้ แต่ในคลังของเราทำได้ตามใจ
3. **ข้อมูลเล็กมาก** PO+GR รวมกันไม่ถึง 600,000 แถว ดึงทั้งหมดใช้เวลาไม่กี่วินาที
4. **เก็บประวัติได้** ถ่ายภาพยอดค้างรับสิ้นวันไว้ ทำกราฟแนวโน้มได้ ซึ่ง ERP ทำไม่ได้

### ทำไม dev เป็น SQLite

เครื่อง dev นี้ไม่มี SQL Server ติดตั้ง และการรอให้ IT สร้าง DB บน server จริงจะบล็อกงานไว้
SQLite เป็นไฟล์เดียว ไม่ต้องติดตั้งอะไร ตอนขึ้น production สลับไป SQL Server 2022
โดยแก้ `WAREHOUSE_KIND` ใน `.env` เท่านั้น ชั้น ETL และชั้นรายงานใช้ SQLAlchemy จึงไม่ต้องแก้โค้ด

## 4. นิยามตัวเลข (ต้องให้จัดซื้อยืนยัน)

| ตัวเลข | นิยามที่ใช้ | เหตุผล |
|---|---|---|
| มูลค่า | **ก่อน VAT** (`AMT`) | จัดซื้อคุมงบที่ราคาสินค้า มี toggle ดูรวม VAT ได้ |
| มูลค่าที่รับ | จำนวนรับสุทธิ x ราคาใน PO | ตรวจแล้วว่า `POC_RCVD.PRICE` เท่ากับราคา PO เสมอ จึงเทียบบนฐานเดียวกัน |
| จำนวนรับสุทธิ | `SUM(QTY)` ของ `DOCTYP IN (R, T)` | หักส่งคืนอัตโนมัติ |
| ค้างรับ | จำนวนสั่ง ลบ รับสุทธิ แต่ไม่ต่ำกว่า 0 | รับเกินต้องไม่กลายเป็นค้างติดลบไปหักยอดบรรทัดอื่น |
| ผ่อนผัน (tolerance) | **บวกลบ 2%** | งานผ้าและม้วนตัดไม่ลงตัว ปรับได้ที่หัว SQL |
| ส่งตรงเวลา | ใบรับ**ใบแรก** ไม่เกิน `ShipDat` | |
| Lead time | วันที่รับใบแรก ลบ วันที่ PO | |
| ไม่นับเป็นค้างรับ | `APPSTS` = A (รออนุมัติ), C หรือ T (ยกเลิก) | |
| วันที่ว่าง | `1899-12-30` แปลงเป็น `NULL` | ค่า TDateTime 0 ของระบบเดิม |

## 5. มุมมองเวลา 2 แบบ ห้ามปนกัน

ของที่รับเดือนตุลาคม อาจมาจาก PO เดือนสิงหาคม ดังนั้น**ห้ามเอากราฟ "สั่ง" กับ "รับ" มาวางคู่กันเฉย ๆ
แล้วบอกว่าเทียบกันได้**

**A — Activity View (ตามปฏิทิน)**
เดือนนี้สั่งไป X บาท / เดือนนี้ของเข้ามา Y บาท (ไม่สนว่ามาจาก PO ใบไหน)
ใช้ดูภาระงานและกระแสเงิน

**B — Cohort View (ตามรุ่น PO)** -- ตัวหลัก
PO ที่เปิดเดือนกันยายน มูลค่า X บาท ตอนนี้รับมาแล้ว 78% ค้าง 22% lead time เฉลี่ย 23 วัน
**ตอบโจทย์จัดซื้อตรง ๆ ว่า "สั่งไปแล้วได้ของมาเท่าไหร่"**

Dashboard ใช้ B เป็นพระเอก มี A เป็นกราฟประกอบ

## 6. รายงาน

### R1 — ใบรับเข้าตามช่วงเวลา (หน้าที่จัดซื้อจะเปิดทุกเช้า)

วันที่รับ | เลขที่ใบรับ | เลขที่ PO | วันที่ PO | ผู้ขาย | รหัสและชื่อสินค้า | จำนวนรับ | หน่วย | ราคา | มูลค่า | ที่เก็บ | เลขเอกสารผู้ขาย | ช้าหรือเร็ว (วัน) | ผู้บันทึก

### R2 — ค้างรับ (Open PO)

PO | วันที่ | ผู้ขาย | สินค้า | กำหนดส่ง | สั่ง | รับแล้ว | คงค้าง | มูลค่าค้าง | เปอร์เซ็นต์รับ | สถานะ | เกินกำหนด (วัน) | รับล่าสุดเมื่อ

ไฮไลต์แดงเมื่อเกินกำหนด มี subtotal ตามผู้ขาย

### R3 — สรุปสั่ง vs รับ รายเดือน

เดือน | จำนวน PO | มูลค่าสั่ง | จำนวนใบรับ | มูลค่ารับในเดือน | มูลค่ารับที่มาจาก PO เดือนนั้น | เปอร์เซ็นต์รับของรุ่น | ค้างสะสมปลายเดือน

### R4 — Supplier Scorecard

ผู้ขาย | จำนวน PO | มูลค่าสั่ง | มูลค่ารับ | เปอร์เซ็นต์ส่งตรงเวลา | Fill rate | เฉลี่ยช้า (วัน) | จำนวนรับเกิน | จำนวนรับขาด | ค้างปัจจุบัน

### R5 — Exception Report

- `RCVQTY` ใน ERP ไม่ตรงกับยอดรวมจริงจากใบรับ (รู้แล้วว่ามี 599 บรรทัด)
- รับเกิน PO เกิน tolerance
- PO ค้างเกิน 90 วันไม่มีความเคลื่อนไหว เสนอให้ปิด
- รับของก่อนวันที่ PO (เอกสารย้อนหลัง)
- วันที่ผิดปกติ เช่น ปี 2038

### Dashboard

KPI: มูลค่าสั่งเดือนนี้ / มูลค่ารับเดือนนี้ / ค้างรับทั้งหมด / ค้างเกินกำหนด / เปอร์เซ็นต์ส่งตรงเวลา 90 วัน / จำนวน exception

กราฟ: แท่งคู่สั่งกับรับ 12 เดือน / โดนัทสถานะ / Top 10 ผู้ขายค้างส่ง / Aging ค้างรับ (ยังไม่ถึงกำหนด, 1-7, 8-30, 31-60, 60+ วัน)

### Export Excel

ทุกรายงานมีปุ่ม Export ได้ไฟล์ `.xlsx` ที่ freeze header, autofilter และจัดรูปแบบตัวเลขเรียบร้อย พร้อมส่งต่อทันที

## 9. คำถามที่ยังค้าง (ต้องถามจัดซื้อ)

1. `APPSTS` ค่า C กับ T คืออะไรกันแน่ (เดาว่ายกเลิก) ถ้าเดาผิด ตัวเลขค้างรับจะเพี้ยน
2. **ปิด PO ด้วยมือได้ไหม** ถ้ารับไม่ครบแล้วไม่มีทางปิด ยอดค้างรับจะพอกตลอดกาล
   ข้อนี้กระทบความน่าเชื่อถือของ R2 มากที่สุด
3. ปี 2021-2023 หายไปไหน (ย้าย DB / ล้างข้อมูล / ใช้ระบบอื่น)
4. ต้องการคอลัมน์ "ที่เก็บ" ในรายงานรับเข้าไหม (ต้อง join `INV_TRN` เพิ่ม)
5. tolerance บวกลบ 2% เหมาะไหม หรือควรต่างกันตามกลุ่มสินค้า
